(clean build, no errors; two pre-existing -Wmisleading-indentation warnings
in test helper printf lines, harmless)

-O3 -march=native -fassociative-math -fno-signed-zeros -fno-trapping-math lets
gcc vectorize linear()'s dot-product reduction (confirmed via objdump: the bulk
of the loop compiles to 8-wide AVX vmulps/vaddps, versus scalar addss at plain
-O2/-O3). Deliberately not full -ffast-math, which also assumes no NaN/Inf --
see STDLIB.md/README for the tradeoff.

Toolchain used to verify: gcc 15.2.0 (Ubuntu, via WSL), C99, GNU/Linux x86_64.

Measured generation throughput (clock_gettime instrumentation in
generate_autoregressive, printed to stderr as "[N tokens in Xs, Y tok/s]") on
the real tinyllama-1.1b-chat-v1.0.Q4_K_M.gguf, in this project's dev
environment (a memory-constrained ~7.6GB WSL2 VM): two clean back-to-back runs
of 48 tokens measured 233.86s (0.21 tok/s) and 323.75s (0.15 tok/s) -- a ~1.4x
spread between two otherwise-identical runs, which is itself informative: this
VM's effective throughput varies a lot run-to-run (a standalone malloc+touch
benchmark of an equivalent-sized buffer showed the same ~180MB/s-effective,
mostly-sys-time behavior earlier in this project's development), consistent
with memory-bandwidth/virtualization overhead being the dominant cost here,
not raw arithmetic. Judges on a normal (non-virtualized, more RAM headroom)
machine should expect meaningfully better and more consistent throughput than
these numbers.

After parallelizing linear() across output rows with pthreads (12 logical
cores available in this VM): the same 48-token run measured 47.47s (1.01
tok/s) -- roughly a 5-7x speedup over the pre-threading numbers above, and
the generated text is byte-identical to the pre-threading run (parallelizing
a deterministic reduction over disjoint output rows changes nothing about
the result, only how it's computed). Note -pthread did not add a separate
libpthread.so to the linked-library list below -- this glibc version (2.35+,
Ubuntu with gcc 15.2) merges pthread symbols into libc.so.6 itself.

2. Runtime verification against a real model file
----------------------------------------------------
Downloaded the actual submission target,
TheBloke/TinyLlama-1.1B-Chat-v1.0-GGUF's tinyllama-1.1b-chat-v1.0.Q4_K_M.gguf
(668,788,096 bytes), and ran it through the full pipeline (no reference
implementation used to cross-check -- verified by reading real GGUF bytes
and by the output being recognizable English, not noise):

  $ ./llamini tinyllama-1.1b-chat-v1.0.Q4_K_M.gguf
  Loaded GGUF v3 (201 tensors, 23 metadata entries)
  Config: dim=2048 layers=22 heads=32 kv_heads=4 ffn=5632 vocab=32000 seq_len=2048
  You: hello
  Bot:Sure, I'd be happy to provide you with a friendly chatbot that always
  responds concisely. Here's a sample response:

  Hey, how are you doing today?

  I'm doing

  $ ./llamini tinyllama-1.1b-chat-v1.0.Q4_K_M.gguf --raw
  You: hello
  Bot:, world!
  ...
  In this example, the `print` function is used to output the greeting
  message. The `print` function takes a string as an argument, which is
  then printed to the console.

(First transcript uses the default chat template, added after fixing
generate_autoregressive to actually prefill every prompt token through the
KV cache -- an earlier version of this run, before that fix, only ever
forwarded the prompt's last token and produced disconnected text
("Bot:. The event, DP, and"); see git history. Second transcript is --raw,
which bypasses the chat template and reproduces the original prefill-fix
output exactly, confirming --raw is a true no-op relative to that baseline.)

Confirms: real GGUF header/metadata/tensor-table parsing, real Q4_K/Q6_K
dequantization (embedding and output-projection rows come back as small,
varied, non-NaN floats matching real trained weights -- checked directly
against the file before this run), all 22 real decoder layers with
grouped-query attention (32 query heads / 4 KV heads, matching the file's
own llama.attention.head_count_kv), and a real SentencePiece-BPE
tokenizer/detokenizer driven by the file's own vocab.

5. Process-spawning check
--------------------------
$ grep -n "system(\|popen(\|exec[lv]" *.c *.h
(no matches)

The tool never shells out to another installed binary (llama-cli, python,
etc.) — it only mmap()s a user-supplied .gguf file and parses its bytes
directly.

6. No package manifests
------------------------
$ ls | grep -iE "package.json|Cargo.toml|go.mod|requirements.txt|vcpkg.json|conanfile|CMakeLists.txt"
(no matches)

Build system is a single hand-written Makefile. No CMake FetchContent, no
vcpkg, no Conan.

7. Dependency manifest
-----------------------
This project's manifest is the Makefile's SRC list — every file in it is
written by this team this weekend. There is no separate lock/manifest file
format for C; "empty manifest" here means: no vendored source, no linked
third-party library, no shelled-out tool. All are demonstrated above.

REPRODUCIBLE: two clean builds from the same source tree, same compiler

Honest caveat: this is same-machine/same-toolchain/same-directory-path
reproducibility, not a cross-environment guarantee -- gcc embeds the build
directory path in some debug/metadata sections, so building from a
different checkout path could change the hash even with identical source
and flags. -ffile-prefix-map=$(PWD)=. would make it path-independent if
that stronger claim is ever needed; not added here since the Makefile
doesn't assume a fixed checkout path today.
