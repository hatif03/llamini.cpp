Zero-Dependency proof — llamini.cpp (Track F)
==============================================
Regenerated 2026-08-31 against the current 9-file build (main.c, tensor.c,
model.c, gguf.c, kv_cache.c, quant.c, tokenizer.c, generate.c, gpt2.c) — the
previous version of this file predated gpt2.c being added to the Makefile's
SRC list and the CPU-optimization pass (persistent thread pool, posix_fadvise/
madvise), so its build transcript and hashes no longer matched what `make`
actually produces. Everything below was captured from real commands just run,
not copied from memory or an earlier version of this file.

(clean build, no errors; three pre-existing -Wmisleading-indentation warnings
in test helper printf lines in main.c, harmless — same warnings as every
prior build of this project, not new)

-O3 -march=native -fassociative-math -fno-signed-zeros -fno-trapping-math lets
gcc vectorize linear()'s dot-product reduction (confirmed via objdump: the bulk
of the loop compiles to 8-wide AVX vmulps/vaddps, versus scalar addss at plain
-O2/-O3). Deliberately not full -ffast-math, which also assumes no NaN/Inf --
see STDLIB.md/README for the tradeoff.

linear() itself has since gained two more layers on top of that base
vectorization (see STDLIB.md's substitution log for the full story, not
repeated here): a persistent worker-thread pool (created once, replacing the
original per-call pthread_create/pthread_join) for eager (small/norm/bias)
tensors, and on-demand row-chunk dequantization straight from the mmap'd GGUF
file for the large weight matrices, instead of materializing every weight to
f32 at load time. Both were verified bit-identical against the pre-change
binary before being kept — see BUILDLOG.md's CPU optimization phase.

Toolchain used to verify: gcc 15.2.0 (Ubuntu, via WSL), C99, GNU/Linux x86_64,
uname -srm: "Linux 6.18.33.2-microsoft-standard-WSL2 x86_64", 12 logical cores.

3. Linked libraries
-------------------
$ ldd llamini
	linux-vdso.so.1 (0x000079d35a0c2000)
	libm.so.6 => /usr/lib/x86_64-linux-gnu/libm.so.6
	libc.so.6 => /usr/lib/x86_64-linux-gnu/libc.so.6
	/lib64/ld-linux-x86-64.so.2

Only libc and libm (the -lm math library, itself part of the standard C
toolchain) are linked. No third-party shared object anywhere in the chain.
Note: -pthread does not add a separate libpthread.so to this list — this
glibc version (2.35+, Ubuntu with gcc 15.2) merges pthread symbols into
libc.so.6 itself. The persistent thread pool in model.c (see section 1) still
uses real pthread_create/pthread_mutex/pthread_cond calls; they're just
resolved from libc.so.6 rather than a separately-listed .so on this system.

4. Includes across every .c/.h in the repo
-------------------------------------------
$ grep -n "^#include" *.c *.h
common.h:  <stdio.h> <stdlib.h> <string.h> <math.h> <unistd.h>
           <sys/types.h> <sys/mman.h> <sys/stat.h> <fcntl.h> <time.h>
           <ctype.h> <assert.h>
model.c:   <pthread.h> (file-scoped: "model.c only -- keep the blast radius of
           adding threading small", per its own comment)
gguf.c:    defines `_POSIX_C_SOURCE 200809L` before its own #include "gguf.h"
           (which pulls in common.h's system headers) -- needed because glibc
           hides posix_fadvise/posix_madvise under -std=c99 without this
           feature-test macro. Both calls are real POSIX.1-2001/2008 (not
           libc-only) hints: POSIX_FADV_SEQUENTIAL during the file's initial
           metadata/tensor-info parse, POSIX_MADV_RANDOM afterward, since
           inference-time tensor access is scattered per-block reads, not
           sequential.
main.c / every other *.c / *.h: only the project's own headers ("common.h",
           "tensor.h", "model.h", "kv_cache.h", "gguf.h", "quant.h",
           "tokenizer.h", "generate.h", "gpt2.h")

Every include is either C stdlib, POSIX (mmap/open/fstat/pthread/fadvise/
madvise family), or an in-tree header. No ggml.h, no llama.h, no vendored
third-party source anywhere in the tree.

5. Process-spawning check
--------------------------
$ grep -n "system(\|popen(\|exec[lv]" *.c *.h
(no matches)

The tool never shells out to another installed binary (llama-cli, python,
etc.) — it only mmap()s a user-supplied .gguf file and parses its bytes
directly.

6. No package manifests
------------------------
$ ls | grep -iE "package.json|Cargo.toml|go.mod|requirements.txt|vcpkg.json|conanfile|CMakeLists.txt"
(no matches)

Build system is a single hand-written Makefile. No CMake FetchContent, no
vcpkg, no Conan. (A real, unmodified upstream llama.cpp was separately built
from source with cmake purely to generate the head-to-head comparison numbers
in README's "Benchmarks" section — that build lives entirely outside this
repo, in a scratch directory, was never vendored/shipped/committed, and cmake
is not required to build llamini.cpp itself. See STDLIB.md's "Benchmark
methodology" section for the full disclosure.)

7. Dependency manifest
-----------------------
This project's manifest is the Makefile's SRC list — every file in it is
written by this team this weekend. There is no separate lock/manifest file
format for C; "empty manifest" here means: no vendored source, no linked
third-party library, no shelled-out tool. All are demonstrated above.

and flags. -ffile-prefix-map=$(PWD)=. would make it path-independent if
that stronger claim is ever needed; not added here since the Makefile
doesn't assume a fixed checkout path today.

9. "Single command, runnable artifact" — no model download required
----------------------------------------------------------------------
`make && ./llamini --test` is a complete, self-contained proof that the build
works: --test constructs a synthetic in-memory model (hand-populated tensors,
no file I/O) and runs every unit test (matmul, RMSNorm, RoPE in both
conventions, KV cache reset, INT4 quant round-trip, a full GQA forward pass
via generate_autoregressive, and malformed-GGUF rejection) entirely
in-process. Ran it just now, right after the section 1 build:

  $ ./llamini --test
  ===== All Unit Tests =====
  [MatMul Test] ... [RMSNorm Test] ... [RoPE Test] ... [KV Cache Test] ...
  [INT4 Quant Test] ... [Tokenizer + Generate Test] ...
  [GGUF Reject Test]
  all malformed files correctly rejected
  =========================

This needs zero downloads and zero external files — README's "Build and run"
leads with this same point. A `.gguf` model file (section 2) is user-supplied
runtime input to the resulting binary (`./llamini model.gguf`), exactly like
any program that opens a file the user provides — not a build dependency, and
not shipped with or required by the build itself.
