# llamini.cpp architecture

A minimal, from-scratch C99 llama.cpp core. Extend existing files. Do not add a `src/` tree or a third-party tokenizer.

## Module map

| File | Role | Current state |
| --- | --- | --- |
| `common.h` | typedefs, limits, BOS/EOS | shared floor |
| `gguf.c` / `gguf.h` | GGUF mmap, real metadata + tensor-info table parser, dequantizer | real: header, all 13 metadata value types (incl. arrays), tensor-info table, alignment-padded data section; dequantizes `F32`/`F16`/`Q4_0`/`Q4_1`/`Q5_0`/`Q8_0`/`Q4_K`/`Q5_K`/`Q6_K`, fails loudly (`-1`) on anything else; parsing is hardened against malformed/hostile files (sane bounds on counts and lengths, no multiply-overflow on array sizes — see `test_gguf_reject` in `main.c`); `gguf_get_str` reads a scalar STRING metadata value (used for `general.architecture`, `tokenizer.ggml.model`); `gguf_open` hints `posix_fadvise(SEQUENTIAL)` during its own parse and `posix_madvise(RANDOM)` afterward; the per-type dequant switch is now internally range-based (`dequantize_range`, taking an element range, block-aligned) so `gguf_dequantize_tensor` (whole tensor) and `gguf_dequantize_rows` (a row range, used by lazy weight loading) share one implementation instead of two |
| `tensor.c` / `tensor.h` | `malloc` tensors, matmul, vec ops, eager/lazy dispatch | implemented; `matmul()` only used by `--test`, not the real forward pass (see `linear()` below); `Tensor` gained two nullable fields (`src_gf`/`src_info`) so a tensor can be **lazy** (`data == NULL`, dequantized on demand from a GGUF file/tensor-info pair) instead of **eager** (`data` calloc'd and fully populated, the only mode that existed before the CPU optimization pass) — every `tensor_create` caller (including `main.c`'s synthetic-weights test) is unaffected, since those two fields default NULL and `data` stays eager exactly as before; `tensor_get_row()` abstracts a single-row lookup (memcpy for eager, single-row dequant for lazy) for embedding-table indexing |
| `model.c` / `model.h` | real config from GGUF (multi-arch), RMSNorm, RoPE (NORM+NEOX), gated FFN (SiLU/GELU), `linear()`, GQA/MQA causal attention, weight loading, CPU optimization | real: `llama_config_from_gguf` reads `general.architecture` (via `gguf_get_str`) and namespaces every hyperparam key as `"<arch>.<suffix>"` (`arch_key()`), so the same loader drives LLaMA, Qwen2, and Gemma; per-arch quirks are set explicitly (`qwen2`→NEOX RoPE + qkv bias, `gemma`→NEOX + GeGLU + embedding scale `sqrt(dim)`); `llama_load_weights` marks the big matmul-weight tensors (embeddings, `lm_head`, every per-layer projection) **lazy** instead of dequantizing them to a persistent `f32` buffer (norms/biases stay eager — too small to matter), skips loading a duplicate output-projection tensor when embeddings are tied; `causal_mha` is GQA/MQA-aware (`group = n_heads/n_heads_kv`, degrades to plain MHA when they're equal) with real softmax; `rope()` implements both NORM (adjacent-pair, LLaMA/Mistral-style) and NEOX (half-split, Qwen2/Gemma-style) conventions; `ffn_glu()` (renamed from `swiglu`) dispatches SiLU vs. GELU gating; `linear()` takes a `Tensor*` (not a raw pointer) and dispatches on eager-vs-lazy: eager tensors use a **persistent thread pool** (workers created once, blocked on a condvar between dispatches — replaced the old spawn-per-call `pthread_create`) parallelized across output rows above a size threshold; lazy tensors go through `linear_lazy()`, which dequantizes fixed-size row-chunks (not thread-count-sized chunks — see the CPU optimization section below for why) on demand via `gguf_dequantize_rows` (`gguf.c`) and runs the same dot product against a small scratch buffer, serially (not thread-pooled — see STDLIB.md for the reasoning) |
| `gpt2.c` / `gpt2.h` | separate GPT-2 forward pass (not a LLaMA variant — no RoPE, no gating, no GQA) | real: its own config/model/load/generate/perplexity functions, reusing `linear()`/`causal_mha()` from `model.c` and `sample_token()`/`greedy_sample()` from `generate.c`; implements learned absolute position embeddings (added at embed time, not RoPE), a fused QKV tensor sliced by pointer arithmetic after one `linear()` call, LayerNorm (mean-centered + bias, unlike RMSNorm), and an ungated GELU MLP; dispatched from `main.c` by peeking `general.architecture == "gpt2"` before the LLaMA-family path even opens the model |
| `kv_cache.c` / `kv_cache.h` | attention cache | init/reset; one instance **per layer** (array in `main.c`), sized by `kv_dim = n_heads_kv * head_dim`, not the full embedding dim |
| `quant.c` / `quant.h` | generic INT4 scale/zp | teaching-only, exercised by `--test`; unrelated to the real `Q4_K`/`Q5_K`/`Q6_K` decoders in `gguf.c` used to actually load models |
| `tokenizer.c` / `tokenizer.h` | real SentencePiece-BPE **and** byte-level BPE encode/decode + hash table | real: `vocab_load_from_gguf` detects `tokenizer.ggml.model` and sets `v->is_bpe`; SPM path (LLaMA/TinyLlama) unchanged — score-ranked merge (O(n^2) rescan), byte-fallback, SPACE-marker (▁) handling; BPE path (Qwen2, GPT-2) builds a `"left right"`→rank hash table from `tokenizer.ggml.merges` plus GPT-2's byte<->unicode remap table (`ByteMap`), and does rank-ranked merging instead of score-ranked — `ponytail:` disclosed: pre-tokenization is a simplified whitespace split, not GPT-2's real Unicode-regex splitter. Public `text_to_tokens`/`token_to_text` dispatch on `is_bpe`. Neither path has a special-token pre-split pass — a literal `"</s>"` in input text does NOT BPE-merge into the real EOS token, verified empirically (see `main.c`'s `build_chat_prompt_tokens` comment) |
| `generate.c` / `generate.h` | full per-layer autoregressive loop, teacher-forced perplexity | real: `forward_step` (embed -> N-layer stack -> final norm -> lm_head) is shared by `generate_autoregressive` (prefills the whole prompt through the KV cache before sampling/appending anything — critical fix, see git history) and `compute_perplexity` (teacher-forced, used by `--bench`); `sample_token` supports temperature + top-p nucleus sampling, `temp<=0` dispatches to the original deterministic `greedy_sample`; in `SRC` |
| `main.c` | CLI, `--test`, `--bench`, chat, architecture dispatch | opens the GGUF file, reads `general.architecture` via `gguf_get_str` before anything else; if `"gpt2"`, runs an entirely separate `GPT2Config`/`GPT2Model` init/load/chat-or-bench block (raw completion only, no chat template) and exits; otherwise falls through to the existing LLaMA-family path (`llama_config_from_gguf` now handles LLaMA, Qwen2, and Gemma via arch-namespaced keys), loads the vocab (SPM or BPE per `is_bpe`), allocates per-layer KV caches, and either chats (`start_chat`, `build_chat_prompt_tokens` wraps input in TinyLlama-Chat's own template unless `--raw` — no chat template exists for Qwen2/GPT-2, so those are always raw-completion) or runs the correctness benchmark (`run_bench`, `--bench`) |

Makefile `SRC`: `main.c tensor.c model.c gguf.c kv_cache.c quant.c tokenizer.c generate.c gpt2.c` → `llamini`. `CFLAGS` includes `-pthread` (used by `model.c`'s `linear()`) and conservative fast-math flags (see Makefile comment).

Config is no longer hardcoded or LLaMA-only — `llama_config_from_gguf` reads `general.architecture` and namespaces hyperparameter keys per-arch, falling back to TinyLlama-1.1B-shaped defaults (dim 2048, 22 layers, 32 heads, vocab 32000) only for keys a file doesn't define. GPT-2 has its own `gpt2_config_from_gguf` in `gpt2.c` since its shape (fused QKV, position embeddings, no GQA) doesn't fit `LLaMAConfig`.

Verified end-to-end on real files, all four now working: TinyLlama-1.1B-Chat (LLaMA), Qwen2.5-0.5B-Instruct (Qwen2, discovered it needs `Q5_0`), GPT-2-124M (discovered it needs `Q5_K`), and Gemma-2b (initially couldn't fit this ~7.6GB dev machine's memory when weights were fully dequantized to f32 — the CPU optimization pass's lazy/on-demand dequantization, see below, fixed that: Gemma-2b now runs reproducibly at ~1.5GB resident). See README's "Other model families" and "CPU optimization", and BUILDLOG.md Phases 4-5.

## CPU optimization (added after the four architectures above were working)

Researched real llama.cpp/ggml source (not guessed) for how it gets CPU speed, then reimplemented the two ideas independently, staying inside libc+POSIX:

1. **Persistent thread pool** (`model.c`): replaced spawn-per-call `pthread_create`/`pthread_join` in `linear()`'s eager-tensor path with a `ThreadPool` (mutex + two condvars + a generation counter), created once. Bit-identical output to the old spawn-per-call version — pure overhead removal.
2. **On-demand row-chunk dequantization** (`gguf.c`/`tensor.h`/`model.c`): the big matmul-weight tensors (embeddings, `lm_head`, every per-layer projection) are no longer dequantized to a persistent `f32` buffer at load time. `Tensor` gained a lazy mode (`src_gf`/`src_info` instead of a populated `data`); `linear()` dispatches to `linear_lazy()` for lazy tensors, which dequantizes fixed `LAZY_CHUNK_ROWS`-sized chunks (not thread-count-sized — a very wide tensor like Gemma's 256128-row embedding table would otherwise need a multi-hundred-MB per-worker scratch buffer, defeating the point) into a small scratch buffer, serially, reusing the existing `linear_range` dot product.

Both changes are verified **bit-identical output** against the pre-change binary for TinyLlama/Qwen2.5/GPT-2 (the acceptance bar, not just "doesn't crash"). Measured effect: resident memory dropped ~6-7x across every model (~4.4-4.9GB → ~700MB-1.5GB) — this is what let Gemma-2b move from untestable to verified. Wall-clock timing on this dev VM was too noisy run-to-run (memory/virtualization overhead dominates) to report a single confident speedup number; see BUILDLOG.md's CPU optimization phase for the actual measurements taken. See STDLIB.md's substitution log for exactly what's simpler here than ggml's real approach (no quantized-activation int8 dot product, malloc/free per chunk instead of a persistent scratch, no thread-pooling of the lazy path).

CLI flags: `--test` (synthetic-weight unit tests), `--bench` (real-model perplexity + fact-completion evidence), `--temp X` (opt-in sampling), `--raw` (skip the chat template).

## Still open (see README limits, do not pretend these are done)

1. ~~Fused/on-demand dequantization~~ — **done** (CPU optimization pass, see above): the big weight tensors dequantize row-chunks on demand instead of materializing to `f32` at load time, verified bit-identical output and a ~6-7x resident-memory reduction. What's still simpler than ggml's real version (no true quantized int8 dot product, no thread-pooling of the lazy path, malloc/free per chunk) is disclosed in STDLIB.md rather than silently left as a gap.
2. Single-turn: every layer's KV cache resets each chat line; no multi-turn conversational memory.
3. Dequantization doesn't cover `Q2_K`/`Q3_K`/`Q8_K` (not used by any real file probed so far, so untested and deliberately left as "unsupported" rather than shipped unverified).
4. `causal_mha`'s attention is still a naive scalar loop (not parallelized — its compute is negligible next to `linear()`'s, and its `static f32 scores[MAX_SEQ_LEN]` buffer would need to become per-thread first).
5. Sampling has no top-k, repetition penalty, or `--seed` for a reproducible sampled transcript.
6. Chat template (`build_chat_prompt_tokens`, `main.c`) is a best-effort reconstruction from TinyLlama-Chat's published `tokenizer_config.json`, not verified against a real `transformers` install (there isn't one — zero deps); it only applies to the LLaMA/TinyLlama-Chat path — Qwen2 (ChatML) and GPT-2 have no template and are always raw-completion.
7. ~~Gemma-2b's full generation is unverified~~ — **done**: now verified end-to-end (see module map above and "CPU optimization"). Mistral was skipped (its GGUF `general.architecture` is literally `"llama"` — zero new code path). Gemma2 and BERT were skipped as scoping decisions (Gemma2 adds real complexity — softcapping, sliding-window attention — for the same memory cost as Gemma1; BERT is a fundamentally different product shape — no causal mask/KV cache, pooled output — not a stretch attempted this pass).

## How to change it

- Match `common.h` typedefs (`f32`, `u32`, …) and existing names (`gguf_open`, `tensor_create`, `llama_model_init`).
- One concern per `.c` / `.h` pair.
- GGUF weight tensors are row-major `(out_dim, in_dim)` — use `linear()` (`model.c`), not `tensor.c`'s `matmul()`, for anything reading a loaded weight tensor.
- Load files with POSIX `open` / `mmap` as in `gguf.c`.
- A user-supplied `.gguf` is untrusted input — validate sizes/lengths before allocating or reading (see `gguf.c`'s bounds checks and `test_gguf_reject`), don't just trust file-controlled counts.
- Name remaining stubs in README limits; do not paper over the memory footprint, missing sampling knobs, or an unverified chat template.
